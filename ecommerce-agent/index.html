SECTION 01

项目背景与目标

真实电商请求常把订单、物流、优惠与售后组合在同一句话中。本项目面向 100 个已知工具，先判断请求是否需要工具，再为电商类请求输出完整的 Top-K 工具集合，支撑后续 Agent 执行。

PARTIAL HITFAIL

“查一下订单详情、物流状态，并帮我确认退款进度。”

GOLD SET order_detaillogisticsrefund_status
TOP-K COVERS order_detaillogisticsrefund_status · MISSING

命中 2/3，但执行链仍不完整。

COMPLETE HITPASS

同一个请求，Top-K 覆盖全部三个必要工具。

GOLD SET order_detaillogisticsrefund_status
TOP-K COVERS order_detaillogisticsrefund_status

Gold ⊆ Top-K，才记为一次成功。

PRIMARY METRIC

AllHit@K

若当前 Query 的全部 Gold Tools 都在 Top-K 中，则为 1；否则为 0。

Gold ⊆ Top-K→ 1
Gold ⊄ Top-K→ 0
K=10 衡量短名单质量；K=30/50 衡量候选覆盖。
01

按请求类型智能分流

入口 Intent Gate 区分电商诉求与开放闲聊，把计算集中在真正需要工具的请求上。

02

以完整集合覆盖为目标

单工具与最多六工具请求采用统一口径，确保任务链所需能力全部进入候选。

03

分阶段提升候选质量

先用混合检索建立高覆盖候选，再以任务内 Reranker 补充 Query–Tool 交互判断。

隔离验证

表达与上下文隔离

训练与测试使用不同表达簇和 context salt。商品、城市、预算等通用场景仍会自然复用，但仅依赖场景骨架的匹配器 AllHit@10 只有 2.92%，模型需要真正理解工具能力。

数据角色

tool_call_trace/train.jsonl 承担模型学习与融合选参；6K Retrieval test 和 9K Intent set 承担统一离线比较。多组模型曾在同一 6K 集合上横向比较，因此它是固定项目基准，不等同于只运行一次的 final holdout。
