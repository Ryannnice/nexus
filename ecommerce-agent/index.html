PROJECT OVERVIEW

一条连续的三阶段实验路线

本项目围绕同一份 100 工具 Catalog 构建一条连续系统链路：Intent Gate 先判断请求是否进入工具系统；BM25、任务内微调 Embedding、Task Reranker 与 RRF 生成高覆盖候选集；Qwen3-4B/8B Planner 再从候选视图或完整目录中输出有序工具 ID 轨迹。

FINAL PLANNER ENDPOINT SetEM / TraceEM · 99.10%

开发集冻结超参数后，Qwen3-8B 以 54K SFT 数据训练，在上游 RAG@10 候选与独立冻结 API 原生 1K 上取得该端点结果。四档规模曲线中的单点最高值为 99.20%，但不用于反向选择最终端点。

MODULE METRICSAccuracy → AllHit@K → SetEM / TraceEM

同一链路中的路由、检索和规划模块分别使用适配任务的固定集合验证；其中 9K / 6K 用于模块方案比较，Planner 正式 1K 不参与选参。样本与用途不同，因此指标不能直接相乘或合并成一个端到端成功率。

PROJECT LOGIC · FOUR DESIGN DECISIONS

01

按请求类型智能分流

入口 Intent Gate 区分电商诉求与开放闲聊，把计算集中在真正需要工具的请求上。

02

以完整集合覆盖为目标

Retrieval 基准中的单工具与最多六工具请求采用统一口径，确保任务链所需能力全部进入候选。

03

分层提升候选质量

先用混合检索建立高覆盖候选，再以任务内 Reranker 补充 Query–Tool 交互判断。

04

从候选集合生成有序轨迹

Qwen3-4B/8B 在 RAG@10 或完整 100 工具视图下选择精确工具集合，并按照用户要求与依赖关系排序。

FOUNDATION 01 · TASK

任务定义与成功口径

真实电商请求常把订单、物流、优惠与售后组合在同一句话中。本项目沿“先分流、再找齐、后排序”的路径推进：从识别电商请求，到覆盖全部必要工具，再生成符合业务依赖的静态有序工具链。

EXPERIMENT 01 · INTENT GATE

先判断请求是否需要进入工具系统
